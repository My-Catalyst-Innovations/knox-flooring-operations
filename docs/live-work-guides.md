# Live operational work guides

`/work-guides` is an authenticated real-work guide for owners, operations staff and installers. It is separate from Training Center's isolated practice missions. It never creates sample customers, jobs, orders, stock, bookings or training-run records. No schema migration is required.

The learner deliberately selects a saved accessible job. Owners and operations can additionally select a purchase order already linked to that job. Search returns at most 100 matches and asks the user to narrow the search when necessary. Refresh rechecks current saved evidence; there is no “mark done” or completion endpoint, and a correction, return, cancellation or reopening can make a previously verified outcome pending again. Existing team work can satisfy outcomes. This is not personal certification, learner history or proof that the learner performed each action.

## Installer authorization and release dependency

An installer needs an explicit saved task with `assignee_id = authenticated user`, `related_job_id = selected job`, and a supported non-cancelled task status (`Open` or `Done`). For a booking-backed task, the booking must have the exact task ID, job ID and booking ID and remain `Confirmed`. Standalone assigned tasks grant the safe job view, but do not imply crew membership or access to a booking's hours. Neither a crew name nor an owner's actual role during installer preview bypasses the assignment requirement. There is no user-to-crew membership schema.

**Deploy this feature with the separately reviewed installer authorization hardening.** The older job/task/file APIs in the `af0faa3` base allow broad installer reads and task self-assignment. Avoiding those APIs in this new UI does not close the older server boundary. In particular, trusted owner/operations assignment must be enforced before an installer can be allowed to use task-based access in production. Booking tasks generated by the existing schedule initially have no user assignee; trusted assignment support is being handled with that hardening, not inferred by this guide.

The guide uses its own safe APIs and renders outside the global `AppLayout`/`useStore`, so the guide itself never fetches the unfiltered job/task lists. The printable work order now uses the same safe DTO and assignment check, including for an installer opening its URL directly. Job financial fields, estimate snapshots, shared portal tokens, provider identifiers and credentials are never selected for this DTO. Only the signed-in user's update messages are returned by the guide. Free-text operational scope/task/material text remains visible to assigned staff as normal work instructions; authors must use those operational fields appropriately.

## Saved outcomes

Warehouse evidence is specific to the selected job, linked non-cancelled order, products and order warehouse:

- Ordered: the selected order is Ordered, Partially received or Received.
- Received: accepted receipt lines cover every ordered quantity and match saved receipt stock movements by product, warehouse and quantity. Damaged/rejected quantities do not count.
- Bin: each full ordered quantity was received into valid named bins, or the full quantity has active/consumed job staging reservations in valid named bins at the same warehouse. Consumed staging allocations retain this historical evidence after issue; released reservations do not count. A later loose bin transfer does not prove receipt allocation. This is evidence of saved receiving/staging location, not a claim of current bin balance after issue.
- Issue: saved net consume/return ledger quantities from that warehouse to the job cover every ordered quantity. A partial issue remains pending; returns linked to the original issue reduce it even when returned to a different warehouse. Historical returns without an original-issue reference leave this outcome unverified. This verifies aggregate job/product quantities, not physical lot provenance or allocation of a particular order when multiple orders supply the same product.

Installation evidence:

- Assignment: an explicit installer task assignment, or a confirmed booking for owner/operations viewing the guide.
- Field update: at least one normal `job_updates` record authored by the signed-in user. The guide's explicit update form saves to that existing table; the author comes from the authenticated account, and stable UUID replay rejects changed actor/job/message.
- Photos: actual saved `job_photos` records at Final Walkthrough or Completed stage. This confirms saved photo records; it does not probe file storage or certify who took them.
- Labor: positive finite hours on the selected job with a matching confirmed booking and matching crew. Installers see only bookings exactly bound to their assigned tasks; hours are team records, not individual payroll/cost data.
- Closeout: Completed/Invoiced job, a valid saved completion date, a nonempty company required-check policy and every configured check saved true. A stage change through owner override without the checks does not satisfy the outcome.

Owners/operations follow existing purchase order, receiving, bin and job action screens. Installer links stay in the safe work order and live guide. Installers can explicitly save field updates; photo, time and final closeout actions are performed through the existing authorized operational process by operations/owner. The guide does not add installer payroll, business-stage mutation, provider calls or accounting writes.

## API

- `GET /api/work-guides/jobs?q=...`: safe accessible job picker (owner/operations/installer).
- `GET /api/work-guides/jobs/:id?order=...`: safe work order, current evidence and own recent updates. Installer requests for warehouse evidence are rejected.
- `GET /api/work-guides/jobs/:id/work-order`: safe printable operational DTO (also allows existing sales work-order access).
- `POST /api/work-guides/jobs/:id/updates`: existing normal job-update semantics, strict `{id: UUID, message: string}` and session CSRF. Transaction rechecks and locks assignment/job/booking before saving. No outcome flags or actor/company selectors are accepted.

Read endpoints use `Cache-Control: no-store`; detail/work-order queries run in read-only repeatable-read transactions. All database access goes through the existing request-scoped tenant DB. Unknown jobs, wrong assignments and cross-company IDs fail closed. Read failures hide stale guide detail in the frontend. Opening/refreshing cannot send messages, synchronize calendars, create invitations, seed records, mutate stages or perform provider probes.

## Validation

Focused evidence tests cover shortages, damaged-only/missing movement evidence, wrong product/job/warehouse, invalid bins and staging, partial issues/returns, missing closeout checks/dates and reopened work. HTTP tests cover actual auth/role middleware, owner preview, strict query/body/CSRF and no completion mutation. Frontend tests cover scoped endpoints, no automatic writes/click-through completion, explicit update replay, atomic job/order selection and stale-detail removal. Real PostgreSQL release tests cover assignment removal during save, exact booking binding, tenant cookie/host and record isolation, safe DTOs, unchanged whole-database snapshots on reads, real receiving progression and cancellation revoking installer access.

Only deliberate local test fixtures are used in automated tests. No Will/Sam access, production imports, provider connection, public signup or live record changes are part of this feature's verification.
